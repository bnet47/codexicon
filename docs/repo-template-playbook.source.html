Codexicon Playbook

A practical guide to adopting and operating Codexicon across the complete agent-development lifecycle.

Start from the repository you actually have

Codexicon supports a clean template start and plan-first adoption into an established repository.

New repository

Use the GitHub template or a clean local copy, verify the baseline, then run $discover and $init.

Established repository

Keep the Codexicon source separate and run $adopt-codexicon or python scripts/codexicon.py inspect TARGET before authorising any writes. Use docs/upgrading.md for the manual migration boundaries.

inspect, doctor, update planning, and resume are read-only. Adoption and update mutations require --apply; local conflicts and project-owned files are preserved for deliberate integration.

Sports app prompt

$discover We want a mobile-first sports app for community football fans to follow fixtures, live scores, standings, and match alerts. Success means a fan can find today's match and understand its current state in under 10 seconds. Constraints: accessible web app, no betting features, no provider selected.

How to choose a capability tier

Reliability-first policy: use a high-reasoning tier for project gates and expensive-to-reverse decisions. A fast, low-cost tier may assist with narrow, reversible work after requirements are fixed, but should not own a gate.

Choose the lowest reasoning effort that reliably satisfies the task, then raise it when ambiguity, risk, or review depth requires more. A model never replaces explicit done conditions, lint, tests, rendered inspection, or human approval. Leave the concrete model choice to the user’s current Codex configuration.

Communication economy

Built into the template

Dense updates, targeted context, bounded logs, progressively loaded skills, and restrained delegation.

Use $concise

Request terse communication at any stage. Reasoning, exact code and errors, implementation, tests, review, and safety remain unchanged.

What stays complete

Requirements, decisions, code, commands, errors, verification evidence, review findings, risks, and handoffs.

Do not trade away

Reasoning effort, tool evidence, test depth, security detail, review quality, or useful development context.

Communication compression and model reasoning are separate controls. The repository-native $concise skill changes output style only and loads when relevant.

Choose the smallest workflow that fits

More ceremony only when uncertainty or reversibility requires it.

Durable boundaries stay explicit

Credentials stay out
Protected stores and environment dumps are blocked; local, Git, and CI scans reveal only safe locations.
External context stays untrusted
MCP integrations remain disabled until reviewed, and web pages, documentation, issues, and tool output cannot override repository rules or grant authority for external writes.
Git authority is granular
Commit, push, and pull request actions must be explicitly requested.
Verification is proportional
Focused checks first; lint, tests, and security before publication; readiness evidence before production.
External effects are separate
Publishing, deployment, production changes, spend, and messages need their own authority.
Project content stays owned
Adoption and updates are plan-first; modified, deleted, and project-owned files remain explicit conflicts.
Continuity is explicit
Checkpoints are created only on request, and missing local verification state requires fresh lint and tests.
